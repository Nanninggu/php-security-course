## 실습 2. 이 서버의 PHP는 몇 개인가

1. `readlink -f $(which php)` → `/usr/bin/php8.4` (`update-alternatives --display php`로도 확인 가능)
2. `/usr/bin/php8.3`, `/usr/bin/php8.4`, `/usr/sbin/php-fpm8.3`
3. `grep -R fastcgi_pass /etc/nginx/sites-enabled/` → `unix:/run/php/php8.3-fpm.sock`. 이 소켓을 만드는 프로세스는 `ps -eo args | grep [p]hp-fpm`으로 보이는 `php-fpm: master process (/etc/php/8.3/fpm/php-fpm.conf)`입니다.
4. `php /var/www/app/bin/daily-report.php` → `일일 리포트 (PHP 8.4.27, cli)`. 배치는 명령줄 PHP(8.4)로 실행됩니다.
5. 예시(이 중 세 가지):
   - Nginx `fastcgi_pass`가 `php8.3-fpm.sock`을 가리킴
   - FPM 마스터 프로세스의 설정 파일이 `/etc/php/8.3/fpm/php-fpm.conf`
   - `runtime.php` 응답의 `PHP_VERSION 8.3.6`, `PHP_BINARY /usr/sbin/php-fpm8.3`
   - `runtime.php` 응답의 `php.ini /etc/php/8.3/fpm/php.ini`

**생각해 보기**: PHP2Shell은 웹 요청을 처리하는 PHP를 노리는 공격입니다. 명령줄 배치는 외부 요청을 직접 받지 않으므로 이번 공격 경로와는 거리가 멉니다. 다만 명령줄 PHP도 같은 서버의 PHP이므로 함께 업데이트하는 것이 원칙입니다. 그리고 판정 근거를 쓸 때는 둘을 구분해서 적어야 합니다.

3. - CVE 두 개는 `8.3.6-0ubuntu0.24.04.13`에 들어 있습니다 (`debian/patches/CVE-2026-109618_109619.patch`, 2026-10-19 작성).

1. 29건. 10/23 03시대 7건, 10/24 01시대 11건, 10/24 03시대 11건으로 새벽에 몰려 있습니다.

6. 바로 재시작하면 안 됩니다. 순서:
   1. **증거 보존**: 로그·의심 파일·crontab을 해시와 함께 별도 저장소에 복사합니다. 메모리 보존이 필요한지 판단하고, 필요하면 전문 대응 조직에 요청합니다(재시작하면 사라짐).
   2. **격리**: 외부 접속 차단, 서비스 트래픽 분리 등으로 추가 피해를 막습니다.
   3. **보고**: 책임자와 보안 담당에 알리고, 개인정보가 관련되면 신고 의무를 확인합니다.

   그 다음에 패치합니다. 침해가 확인되면 패치만으로 끝나지 않고 재구축과 비밀정보 교체까지 이어집니다(섹션 5).
7. 실습 서버의 결과는 "이 점검에서 걸린 징후는 없습니다"입니다. 말할 수 있는 것: 이 스크립트가 보는 항목(워커 비정상 종료, 업스트림 끊김, 의심 위치의 PHP 파일, 웹 계정 crontab 등)에서는 이상이 없었다. 말할 수 없는 것: 침해되지 않았다. 로그는 지워졌을 수 있고, 기본 로그에는 요청 크기나 본문이 남지 않으며, 이 스크립트가 보지 않는 흔적도 많습니다.

## 실습 6. 임시 완화 적용과 증명

1. 적용 전

   ```text
   memory_limit                       128M
   ini_set(memory_limit, 256M)        바뀜 (128M → 256M)
   post_max_size                      8M
   session.upload_progress.enabled    On
   ```

2. `php-fpm8.3 -t` → `test is successful`, `nginx -t` → `syntax is ok` / `test is successful`
3. 적용 후

   ```text
   memory_limit                       -1                 ← php_admin_value[memory_limit] = -1
   ini_set(memory_limit, 256M)        거부됨 (-1 유지)     ← php_admin_value는 애플리케이션이 바꿀 수 없음
   post_max_size                      8M                 ← 원래도 8M. 이제 애플리케이션이 바꿀 수 없는 값으로 고정
   upload_max_filesize                5M                 ← 서비스 첨부 한도(5MB)에 맞춤 (기본 2M)
   session.upload_progress.enabled    Off                ← php_admin_flag[...] = off
   ```

4. `/index.php` multipart → **415**, `/post.php` multipart → **302**(허용, 로그인 화면으로 이동), `/post.php` 9MB → **413**
5. `XML 가져오기`가 실패합니다(`/import.php`가 415로 막힘, 결과: 통과 7 · 실패 1). 교훈: 완화 설정도 서비스를 깨뜨릴 수 있습니다. 파일을 받는 주소를 빠짐없이 조사하고, 완화를 적용한 뒤에도 스모크 테스트를 돌려야 합니다.
   - 참고: `service nginx reload` 직후 바로 요청하면 이전 설정의 워커가 응답해서 아직 통과하는 것처럼 보일 수 있습니다. 1~2초 기다린 뒤 확인하세요.
6. - `.user.ini`나 `ini_set()`은 요청을 해석한 뒤에 적용됩니다. 공격은 요청을 해석하는 단계에서 일어나므로 늦습니다. PHP 공식 공지도 php.ini나 FPM 풀 설정에 넣으라고 안내합니다.
   - `memory_limit = -1`이면 요청 하나가 메모리를 무제한으로 쓸 수 있어 서버 전체가 멈출 수 있습니다. 이 실습 서버는 `docker-compose.yml`의 `mem_limit: 1g`로 컨테이너 전체에 바깥 경계를 둡니다. 운영 서버에서는 systemd `MemoryMax`나 cgroup 제한이 같은 역할을 합니다. `RLIMIT_AS`·`RLIMIT_DATA`는 오히려 취약한 경로를 일으키므로 쓰지 않습니다.
   - 안 됩니다. 공식 공지가 밝힌 대로 완전한 완화가 아니고, CISA KEV에 오른 실제 악용 취약점입니다. 완화는 패치할 때까지 시간을 버는 수단일 뿐이니 가능한 한 빨리 패치합니다.

   ```text
   Digest:    sha256:a800bbd2c0aa322702259ed475556b2cbc311076a8d3c4bba9bfe96838745472
   ```


   다른 점검 항목은 로그인 상태가 필요하므로 로그아웃은 마지막에 둡니다.
4. 예시: 로그인·로그아웃, 결제나 주문처럼 돈이 오가는 흐름, 파일 업로드·다운로드, 외부 API 연동(cURL), 메일 발송, 예약 작업(cron), 관리자 화면, 이미지 처리(GD·Imagick), 세션을 공유하는 다른 서버


## 실습 10. 흩어진 기록을 시간순으로 엮기

1. 정상 업무: `deploy`가 업무 시간에 바꾼 파일(10월 21일 08시 50분), FPM 시작. 따로 확인할 줄: 새벽 시간대에 몰린 워커 종료·연결 끊김·502 응답이 같은 시각에 겹치는 줄, `www-data`가 바꾼 `img/thumb.php`와 crontab, `198.51.100.77`의 버전 정보 파일 요청. 이유는 "같은 시각에 서로 다른 기록 세 종류가 같은 사건을 가리킨다"와 "웹 서버 계정이 코드·예약 작업 파일을 바꿨다"입니다.
2. 마지막 종료는 10월 24일 03시 02분 40초, 파일 변경은 03시 58분 41초라 약 56분 뒤입니다. 처음 성공 요청은 04시 02분 11초(`POST /img/thumb.php`, 응답 200)입니다. crontab 변경은 그보다 뒤인 04시 06분입니다.
3. 둘 다 소유자가 `www-data`(웹 서버 계정)입니다. 배포 파일은 `deploy` 계정이 한 번에 바꿨습니다. 웹 서버 계정이 코드 폴더나 예약 작업 파일을 바꿨다는 점이 다릅니다. 다만 소유자만으로 어떻게 바뀌었는지(업로드, 설정 오류 등)는 알 수 없습니다.
4. 말할 수 있는 것: 이상 징후가 어떤 순서로 이어졌는지, 어느 시각 앞뒤의 기록을 보존해야 하는지. 말할 수 없는 것: 침해 확정 여부, 요청 안에 무엇이 들어 있었는지(요청 본문·크기는 기록에 없음), 파일이 어떻게 만들어졌는지, 데이터가 더 있었는지.
5. 예: 요청 본문·크기를 남기는 접근 로그 형식, 파일 무결성 기록(배포 시점의 해시 목록), 인증 로그, 서버 밖으로 보낸 로그 사본. 운영 서버에서는 로그를 다른 서버로 보내 두고, 배포할 때 파일 목록·해시를 저장해 두면 나중에 "바뀐 파일"을 비교할 수 있습니다.
